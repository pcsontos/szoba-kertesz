# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project status

Working agent, built as an Nx monorepo. `packages/core` (agent logic), `packages/db` (Prisma), and `apps/cli` (CLI) are scaffolded and functional: the full chain — CLI `ask` → `askAgent` tool-use loop → `runSql` / `listCategories` tools → read-only Postgres — runs and answers real catalog questions in Hungarian. Since the 04. alkalom there is a **second agent**: `ingest` (`pnpm cli ingest "<utasítás>"`) maintains the catalog through a single validated write path (`upsertProduct`) on its own read-write DB role, and can read a live Shopify feed (`fetchFeed`). Both agents run the *same* loop (`agents/agent-loop.ts`).

Since the 05. alkalom the agent **left the terminal**: there are two new entry points — `apps/server` (a thin Express layer, `pnpm serve:api`) and `apps/web` (Vite + React chat, `pnpm serve:web`) — and the shared loop runs on `streamText`, so the browser receives the answer token by token. This **confirms** the framework-agnostic-core invariant rather than contradicting it: `packages/core` did not change for the server's sake; the same `askAgent` runs from the CLI and from HTTP, and the server only translates the request into an agent call. The query agent also gained a **role**: as `admin` it gets one more tool (`delegateToIngest`), with which it can hand a catalog change over to the ingest agent.

Since the 06. alkalom the query agent has **two knowledge sources**, not one. Beside the catalog (SQL over `products`) there is now a **knowledge base**: 202 downloaded plant-care articles under `seed/knowledge/` (a repo **gyökerében**, nem a `packages/db` alatt), chunked and embedded into a `knowledge_chunks` table (pgvector, **1906 chunks** × 1536 dimensions). Since the HF3 work every chunk carries a **breadcrumb prefix** in its own text (`How To Care for a Snake Plant › Water`), and body-less label chunks are dropped — measured: 2041 → 1906 darab, and the share of chunks containing their own article title went 57% → 100% (`docs/chunking-strategia.md`). The `searchKnowledge` tool puts that base in the model's hands, behind a full RAG pipeline (HyDE → embedding → pgvector top-20 → rerank → top-5). The split is the point: **the catalog answers "what do we sell", the knowledge base answers "how do I care for it"** — and the `<grounding>` block forbids answering care questions from the model's own memory.

Since the 07. alkalom (A+B fázis) the conversation **survives the process**. Two new tables (`threads` + `messages`, the whole `UIMessage.parts` JSON) and a **fourth** DB role (`szoba-kertesz_chat`) carry a conversation store that lives in `packages/core/src/lib/threads/` — used by **both** entry points: the web chat and the CLI's interactive mode write into the *same* table, so a conversation started in the terminal can be opened in the browser (`?thread=<uuid>`) and a browser conversation continued in the terminal (`pnpm cli --thread <uuid>`). The `/api/chat` contract changed with it: only the **new** message goes up, the history comes from the database — a forged history sent from the browser has no effect. The tool side also moved: `queryCustomers` (a real `customers` table, 20 seeded customers) replaced the hard-coded `getClientPreferences`. Deliberately left out of this round: the C and D phases of `docs/implementacios-terv.md` (evaluation and deployment).

Since the 08. alkalom the project has a **measuring instrument**, not a new product feature. `tools/autotest` (a separate workspace package, **not** `packages/core` and **not** `.claude/`) holds a Playwright „difficulty ladder" (`battery.ts`: 11 tiers / 29 cases, from single-step to jailbreak and RAG-grounding) and a RAGAS-style RAG evaluation (`rag-eval.ts`: six metrics on the real `retrieveKnowledge` pipeline). The `.claude/skills/autotest/SKILL.md` closes the loop — run → report → ask → **ADR** (`docs/adr/`) — and the code lives outside `.claude/` on purpose: there neither lint, typecheck nor CI would reach it, and this is exactly the code that can report a FALSE GREEN. **`packages/core` did not change by a single line in this round** (measured: empty diff), which is the invariant restated: the measuring instrument is not part of the product.

Since the 09. alkalom there is a **fourth entry point**, and it turns the direction around. `apps/mcp` is a stdio **MCP server**: until now *we* called the model (CLI, HTTP, browser), here a **foreign host** (Claude Code / Claude Desktop) calls *our* tools. Three of them, deliberately in three different styles: `search_plants` (a **data tool** — structured filters → one parameterized `SELECT` → raw rows, no model in it), `search_knowledge` (a **rewired core tool** — the existing `executeSearchKnowledge` translated to MCP shape, same HyDE → embedding → pgvector → rerank pipeline) and `ask_szobakertesz` (**agent-as-tool** — behind one tool call our whole query-agent loop runs, with our prompt and our SQL rules). The security claim of the round: `ask_szobakertesz` is pinned to `role: 'customer'` and `print: false`, because as `admin` the query agent would get `delegateToIngest` and a foreign host's model could **write** to the catalog through MCP; a spec pins both over a real MCP call (`InMemoryTransport`). `queryCustomers`, `upsertProduct`, `delegateToIngest` and the `threads`/`messages` store are deliberately **not** exposed, and no MCP call persists anything. **`packages/core` did not change by a single line in this round either** (measured: empty diff) — a new surface is a new app. Full detail: `docs/mcp.md`.

Ebben a körben (2026-09-03, a 07. alkalom C fázisának koncepciója) az agent-szám **négyre** nőtt, és az első belépési pontok is átkerültek egy irányító réteg mögé. Az `askOrchestrator` (`agents/orchestrator-agent/`) a **harmadik** agent, de más fajta, mint a többi: sosem válaszol saját szóval, hanem pontosan egy toolt hív (`routeToPackageAgent` vagy `routeToInfoAgent`), és a lefutott route-tool jelentését adja vissza szó szerint. Az `askInfoAgent` tool (nem önálló agent — a meglévő `askAgent`-et csomagolja) a katalógus + tudásbázis kérdésekhez, mindig `role: 'customer'`-ként, a külső beszélgetés szerepétől függetlenül; a **negyedik** agent, `askPackageAgent` (`agents/package-agent/`) a csomag-építő — `validatePackage`/`savePackage`/`cancelPackage` toolokkal, sosem fut SQL-t közvetlenül. Mindkét CLI-belépés (`ask`, interaktív mód) és a szerver `POST /api/chat`-je is **mostantól `askOrchestrator`-t hív**, nem `askAgent`-et közvetlenül — a szerver a `role: 'customer'` pinnelését ugyanígy megtartja. A **flow-lock** (`orchestrator-agent/flow-lock.ts`, `findLastFlowSignal`) költség miatt kritikus: ha a history utolsó jelző-toolja `routeToPackageAgent` (a csomag-flow tehát nyitva), az orchestrátor SAJÁT LLM-hívása ki sem megy — egyenesen a package-agentet hívja, így egy N-köríves csomag-építés egyetlen plusz LLM-hívásba kerül, nem N-be. Az **ötödik** DB-szerep (`szoba-kertesz_package`, `DATABASE_URL_PACKAGE`) a `packages`/`package_items` táblákra ír — **append-only**, mint a `_chat` szerep: SELECT + INSERT, sem UPDATE, sem DELETE.

The `docs/` files remain the authoritative spec; `docs/implementacios-terv.md` tracks the phase plan, `docs/HF1-hazifeladat.pdf` is the course assignment and `docs/hf1-hianyossagok.md` (gitignored) the running gap analysis. `docs/hf3-leadas.md` walks the HF3 assignment point by point (what it asked, where it is fulfilled) — start there when the question is "did we submit X". **Four HF3 deliverables live in `docs/` too:** `ARCHITEKTURA.md` (the knowledge base *maintenance plan* + the data-flow SVG in `docs/img/` — not the monorepo layout, which moved to `architektura-monorepo.md` because this filesystem is case-insensitive and the two names would collide), `chunking-strategia.md` (what we measured on the corpus and what followed from it), `golden-set.md` (raw vector search vs. the full pipeline, with the negative test) and the two generated measurements under `docs/golden/`.

### Commands

- **Local DB:** `docker compose up -d` (Postgres on host `5433`), then `pnpm db:migrate` + `pnpm db:seed` (schema + 30 plants + 20 customers; these are the `prisma migrate deploy` / `prisma db seed` wrappers — the same commands, without the `pnpm exec prisma` prefix). `pnpm db:reset` is the **destructive** one (`prisma migrate reset`): it drops every table, so the knowledge base's 1906 chunks go with it and `pnpm knowledge:ingest` has to be re-run — that call costs money. Since the 04. alkalom the two agent roles (`szoba-kertesz_ro`, `szoba-kertesz_rw`) and their grants live in a **migration** (`<ts>_db_roles`), not only in `init.sql`: `init.sql` runs only on the container's first start, so after a `prisma migrate reset` the roles would survive but their grants would not. `migrate deploy` is therefore enough for a fresh DB too.
- **Build & run:** `pnpm cli ask "<kérdés>"` runs straight from source via `tsx` (no build). The `--conditions=@szoba-kertesz/source` flag in that script is load-bearing: it activates the `@szoba-kertesz/source` export condition in `packages/core/package.json`, so `@szoba-kertesz/core` resolves to `src/index.ts`. **Without the flag `tsx` falls back to `packages/core/dist/index.js`** — i.e. it would silently run a possibly stale build of `core` while only `apps/cli/src` came from source. `pnpm nx run cli:build` + `node apps/cli/dist/main.js ask "<kérdés>"` (or `pnpm szobakertesz ...`) still works for the built path. No-arg run starts interactive mode; `--show-prompt` dumps the full system prompt + message array, `--quiet` silences the live Trace. **Interactive mode is persistent** (07. alkalom): it opens a thread lazily at the first question, prints its id, and `pnpm cli --thread <uuid>` continues an earlier conversation — including one started in the browser. The one-shot `ask` deliberately persists nothing.
- **Katalógus-kezelés (ÍR az adatbázisba):** `pnpm cli ingest "<utasítás>"` — the ingest agent (`runSql` + `fetchFeed` + `upsertProduct`). Same `tsx`/`--conditions` mechanics as `ask`; `--quiet` works here too. It writes on the `szoba-kertesz_rw` role, so `DATABASE_URL_READWRITE` must be set; without it the ask/query side still works fully and only `ingest` fails, with an explicit Hungarian message.
- **Tudásbázis felépítése (06. alkalom):** `pnpm knowledge:ingest` — beolvassa a `seed/knowledge/*.md` cikkeket, alcím-határon darabolja, OpenAI-jal vektorizálja (100-as kötegekben) és beírja a `knowledge_chunks` táblába. **Teljes újraépítés** (TRUNCATE + újratöltés), nem inkrementális: kis korpusznál ez a helyes válasz. Valódi OpenAI-hívásokat indít, tehát fizet — a katalógus-oldal enélkül is teljesen működik, csak a `searchKnowledge` bukik el érthető magyar üzenettel.
- **Golden set futtatása (HF3):** `pnpm golden:run --label <név>` — a `seed/golden-set.json` 9 kérdését kétszer futtatja **ugyanazon** a `retrieveKnowledge`-en (nyers: se HyDE, se rerank — teljes: mindkettő), a két negatív kérdésnél plusz egy valódi `askAgent`-futással, és a `docs/golden/futas-<név>.md`-be írja az eredményt. **Fizetős**: kérdésenként 2 embedding + 1 HyDE + 1 rerank. Az érvénytelen `--label` egyetlen API-hívás előtt, magyar üzenettel áll meg. Az elemzés kézzel íródik: `docs/golden-set.md`.
- **Mérőeszköz (08. alkalom) — FIZETŐS:** `pnpm autotest:battery` a Playwright nehézségi létra (11 fok, 29 eset) a **valódi** web UI-n; előfeltétele futó `serve:api` + `serve:web`. Kapcsolók: `--only "<fok-részlet>"` · `--no-hud` · `--consistency` (**alapból KI** — a kurzussal ellentétben, mert nálunk minden futás valódi pénz) · `--keep-threads` · `--dump-cases` (**ingyenes** séma-igazolás, böngésző-indítás nélkül). A futás `logs/autotest/<ts>-battery.json`-t (gépi igazságforrás) és `.md`-t ír, és a végén **eltakarítja a saját threadjeit** admin kapcsolaton — a `_chat` szerep nem tud törölni, és a négy demó-beszélgetés érintetlen marad. `pnpm autotest:report <run.json> [suggestions.json]` a HTML-riport; `pnpm autotest:rag` a RAGAS-mérés (hat metrika, judge `claude-haiku-4-5`-ön, JSON **és** HTML egyben). A hurkot a `/autotest` skill vezeti.
- **MCP-szerver (09. alkalom):** `pnpm mcp` a stdio MCP-szerver — **nem te indítod kézzel**, a HOST indítja (`.mcp.json`; a minta a commitolt `.mcp.example.json`, másold `.mcp.json` néven — az gitignore-olt). Forrásból fut `tsx`-en, sosem `dist`-ből, ezért az `apps/mcp`-nek **nincs `build` targetje** (`tsconfig.app.json`, nem `.lib.json`) — a `run-many -t build` szó nélkül kihagyja, ez nem hiba. `pnpm mcp:smoke` az **ingyenes** bemelegítés-és-ellenőrzés (valódi MCP-kliens, `listTools` + egy `search_plants` hívás; modellt NEM hív), `pnpm mcp:inspect` az MCP Inspector a `6280`/`6281` porton (az alap `6274` ütközne). Előfeltétel ugyanaz, mint a CLI-nél: futó Postgres + `.env`. Költség: `search_plants` **ingyenes**, `search_knowledge` ≈ pár cent, `ask_szobakertesz` ≈ 3–8 cent. A bekötés (Claude Code / Claude Desktop) és a két stdio-csapda: `docs/mcp.md`.
- **Embedding-szemléltető (06. alkalom):** `pnpm embed:demo` — 14 mondat valódi embeddingje és a koszinusz-távolság-mátrixuk az `embed-demo.json`-be (gitignore-olt, nem kommitolt artifact). Semmilyen kód nem függ tőle. Mérve: az angol szinonimapárok 0,21–0,23-on állnak, a magyar–angol jelentéspárok 0,57–0,58-on, a témában idegen bolti szöveg 0,88–0,91-en — **a nyelv maga is erős jel a vektortérben**, és pont ezt a szakadékot hidalja át a HyDE angol nyelvű hipotetikus válasza.
- **RAG debug-végpontok (06. alkalom):** a `pnpm serve:api` mellett `GET /debug/knowledge/sources` (milyen dokumentumok, hány darabban), `/sources/:id` (egy dokumentum a chunkjaival és a teljes szöveggel — így LÁTSZIK, hol vágtunk) és `/chunks[?search=…][&topK=N][&pipeline=full]`. A `search` nélküli hívások **csak a DB-t olvassák**, ingyenesek; a `?search=` egy embedding-hívást, a `&pipeline=full` egy HyDE- és egy rerank-hívást is indít. **Élesben NINCS mountolva** (`NODE_ENV === 'production'`): nyitott `cors()` mögött ez hitelesítés nélküli fizetős végpont lenne. Egy spec pinneli a 404-et.
- **Szerep (05. alkalom):** `pnpm cli ask --role admin "<kérdés>"` (values: `customer` | `admin`; default `customer`). As `admin` the query agent's toolset gains `delegateToIngest`, so a catalog change can be handed to the ingest agent *from the ask side*. The default is the `CURRENT_ROLE` constant in `user-role.ts` — rewriting that constant is the live demo, the flag is for one-off runs. An invalid value fails with a short Hungarian message before any API call. The flag works in interactive mode too (`pnpm cli --role admin`).
- **Web chat (05. alkalom, protokollt váltott a 06.-ban, szerződést a 07.-ben):** `pnpm serve:api` starts the Express server (`http://localhost:3000/api/chat`, `POST { message: UIMessage, threadId?: uuid }` → `text/event-stream`, AI SDK message stream) and `pnpm serve:web` the Vite dev server (`http://localhost:4200`). Two more routes since the 07. alkalom: `GET /api/threads` (the list) and `GET /api/threads/:id` (one conversation with its messages) — both free, DB-only, and mounted in production too, unlike `/debug/knowledge`. Both are needed for the browser chat; the web app talks to `VITE_API_URL` (default `http://localhost:3000`). The server calls `askAgent` with `print: true`, so the **full colored Trace runs on the server console** — the browser only gets the answer text.
- **Tests:** `pnpm nx test core` / `cli` / `server` / `web` (Vitest). Some `core` specs hit the real local DB via `DATABASE_URL_READONLY`, `DATABASE_URL_READWRITE` and — since the 06. alkalom, for `knowledge-store.spec.ts` — `DATABASE_URL`, so the DB must be up + seeded (and migrated, for `pgvector`) for them to pass. The `server` and `web` specs need neither a DB nor an API key: the server's `ask` is injected and the web tests render in jsdom. **Known flake, not a regression:** `db-readonly.spec.ts`'s "row count is unchanged" assertion races against `upsert-product-db.spec.ts`, which inserts real rows in a parallel worker — if that single test fails on a row-count mismatch, re-run before investigating. Two of them prove DB-level guarantees that no mock could: `db-readwrite.spec.ts` (the write role can UPDATE but cannot DELETE or ALTER) and `upsert-product-db.spec.ts` (two **concurrent** upserts on one latin name leave a single row, and a duplicate INSERT is rejected by the index). The latter works on its own throwaway latin names and cleans up over an **admin** connection — the `szoba-kertesz_rw` role deliberately cannot DELETE, so the test could not remove its own rows.
- **Typecheck / lint:** `pnpm nx run <core|cli|server|web>:typecheck` / `:lint`, or all of them at once: `pnpm nx run-many -t typecheck lint build`.
- **CI:** `.github/workflows/ci.yml` — `lint` + `typecheck` + `build` minden PR-en és `master` pushon, **plusz egy célzott `pnpm nx test autotest` lépés** (08. alkalom). A teljes `test` **szándékosan kimarad**: több `core` spec valódi, seedelt Postgresre támaszkodik, ami a runneren nincs. Az `autotest` a kivétel, mert a specjei tiszták (se DB, se API-kulcs, se böngésző — mérve: érvénytelen `DATABASE_URL`-lel és minden kulcs nélkül is zöldek), és mert pont az a kód, ami HAMIS ZÖLDET tud jelezni. A `run-many -t test` továbbra sem jó: az behúzná a `core` DB-s specjeit. A CI-t lokálisan a `pnpm nx run-many -t lint typecheck build` + `pnpm nx test autotest` reprodukálja.
- **Claude PR-review kérése:** `pnpm pr:review` (leszedni: `pnpm pr:review:off`). A `claude-review.yml` **igény szerint** fut, nem minden pushra — egy review ~11 perc valódi API-költség. A script a `claude-review` címkét teszi a branchhez tartozó PR-re, és a címke felrakása indítja a workflow-t; ugyanez a címke újbóli felrakása újraindítja. Előfeltétele az `ANTHROPIC_API_KEY` repo-secret. A Claude Code GitHub App **nem** kell: a workflow a beépített `GITHUB_TOKEN`-nel hitelesít (ezért a kommentet a `github-actions[bot]` írja).

### Key files

The layout is the teaching map: **one concept = one directory**, the shared piece lives one level up. Directory = an instance, file = the common base.

- `packages/core/src/lib/agents/agent-loop.ts` — **the** loop, in one place. `runAgentLoop` + `AgentDefinition`; built on the Vercel AI SDK 7 `streamText` with `stopWhen: isStepCount(n)`. Every agent runs this one; the loop does not know which agent it runs or which tools exist. The Trace hangs on the `prepareStep` (what we send) / `onStepEnd` (what happened) hooks, and the JSONL logger is called at the end. `AskOptions.onTextDelta` hands every text chunk out as it arrives — that is what the server writes to the response.
- `packages/core/src/lib/user-role/user-role.ts` — WHO is talking to the agent: `USER_ROLES`, `CURRENT_ROLE` (`'customer'`), `isAdmin()`. The role switches a **capability**, not a prompt prohibition, and lives one level above `agents/` because it is the outermost concept.
- `packages/core/src/lib/agents/query-agent/` — `query-agent.ts` (`askAgent`: `runSql` + `listCategories` + `queryCustomers`, and **as admin** `delegateToIngest` as well) and `query-prompt.ts` (the product system prompt + the appended `ADMIN_PROMPT_BLOCK`). It never writes itself: the write happens inside the other agent.
- `packages/core/src/lib/agents/ingest-agent/` — `ingest-agent.ts` (`askIngestAgent`: `runSql` + `fetchFeed` + `upsertProduct` — **no** `listCategories`) and `ingest-prompt.ts`. This is the writing agent.
- `packages/core/src/lib/agents/orchestrator-agent/` — `orchestrator-agent.ts` (`askOrchestrator`: a belépési pontok új első hívása, flow-lock rövidzár), `orchestrator-prompt.ts` (a prompt, ami kimondja: sosem válaszol saját szóval), `flow-lock.ts` (`findLastFlowSignal` — tiszta függvény, a history utolsó jelző-toolját olvassa ki).
- `packages/core/src/lib/agents/package-agent/` — `package-agent.ts` (`askPackageAgent`: `askInfoAgent` + `validatePackage` + `savePackage` + `cancelPackage`, sosem `runSql` közvetlenül) és `package-prompt.ts`.
- `packages/core/src/lib/tools/package/` — a csomag-építés toolkészlete: `package-schema.ts` (a `validatePackage`/`savePackage` közös Zod-bemenete), `package-validation.ts` (`checkPackage` — a determinisztikus ellenőrzés, megosztva a validate és a save tool között), `validate-package-tool.ts`, `save-package-tool.ts`, `cancel-package-tool.ts`, `db-package.ts` (az **ötödik** `pg` pool, kizárólag `DATABASE_URL_PACKAGE`-on, tranzakció-helperrel, mert a `savePackage` két táblába ír egyszerre).
- `packages/core/src/lib/tools/ask-info-agent/`, `route-to-package/`, `route-to-info/` — agent-mint-tool csomagolók: az első a package-agent kapuja a query-agent felé (mindig `role: 'customer'`), a másik kettő az orchestrátor két, egymást kizáró route-tool-ja. Csak a `route-to-info/` kap `role`-t az orchestrátor hívójától és adja tovább — a `route-to-package/`-nak nincs rá szüksége, a package-agentnek nincs role-fogalma.
- `packages/core/src/lib/tools/<tool>/` — every tool with **all** its ingredients: `run-sql/` (`run-sql-tool.ts`, `sql-guard.ts` — SELECT-only guard that wraps queries in a subquery to force `LIMIT`, `db-readonly.ts` — the single readonly `pg` pool), `list-categories/`, `query-customers/` (`customer-schema.ts` + `query-customers-tool.ts` — the shop's clients from the `customers` table; it **replaced** the hard-coded `get-client-preferences/`, which is gone), `upsert-product/` (`product-schema.ts` strict Zod + `PRODUCT_COLUMNS`, `db-readwrite.ts`, `upsert-product-tool.ts` — the **only** write path), `fetch-feed/` (`shopify-feed.ts` engine + `fetch-feed-tool.ts`), `delegate-to-ingest/` (`delegate-to-ingest-tool.ts` — the ingest agent wrapped as a tool; the **only** delegation path, it never throws, and its `run` option is the test seam that keeps the specs API-free).
- `packages/core/src/lib/rag/` — a **tudásbázis** hat modulja, a pipeline sorrendjében: `chunk.ts` (markdown darabolása alcím-határon, ~1000 karakter, átfedéssel — a darabhatár ne vágjon ketté egy gondolatot; a HF3 óta **címsor-útvonal** kerül minden darab elé `docTitle` megadásakor, és a törzs nélküli, csak-címke darabok kiesnek — a 60 karakternél hosszabb címsor viszont törzsnek számít, mert a cikkek bevezetője gyakran `######`-tal formázott mondat), `embed.ts` (szöveg → 1536 szám; **az EGYETLEN nem-Anthropic hívás a rendszerben**, mert embedding-modellt az Anthropic nem ad), `knowledge-store.ts` (a vektorkeresés EGY SQL-ben, `<=>` koszinusz-távolsággal; **két pool**: keresés a `_ro` szerepen, betöltés adminon), `hyde.ts` (a kérdésre kitalált hipotetikus válasz **angolul**, mert a korpusz angol — ezt embeddeljük a kérdés helyett), `rerank.ts` (a top-20-at `claude-haiku-4-5` rangsorolja át `generateObject`-tel — kézzelfogható modell-routing: a drága modell válaszol, az olcsó válogat), `retrieve.ts` (a pipeline összekötve, lépésenként láthatóan a Trace-ben).
- `packages/core/src/lib/threads/` — a **beszélgetés-tár** három modulja: `db-chat.ts` (the fourth `pg` pool, `DATABASE_URL_CHAT` only), `thread-store.ts` (four parameterized statements + the `ThreadStore` port that the surfaces' tests inject, and `ThreadIdSchema` — the UUID guard at every boundary) and `message-parts.ts` (`textToParts` / `partsToText`: **the store is one, the views are two** — the browser gets the parts back exactly, the terminal gets the text flattened out of them). It lives in `core` and not in `apps/server` because **two** entry points use it; a store is not a framework.

Interactive mode is the **query agent's** (a conversation with history); `ingest` is deliberately one-shot. `lib/parse-role.ts` and `lib/parse-thread.ts` validate `--role` / `--thread` at the system boundary. That regression is pinned by a test on the pure function; a value-less `--role` still fails fast, because `splitCliArgs` reports the switch's **presence** (as `''`), not `undefined`.
- `apps/server/src/{app,main}.ts` — the Express layer, deliberately split in two: `app.ts` only **builds** the app (side-effect free, with an injectable `ask`), so the route contract can be tested over real HTTP without an API call; `main.ts` is the **boot** (`.env`, fail-fast `loadConfig`, watch log, `listen`). A missing API key would otherwise only surface on the first request. **Since the 07. alkalom `POST /api/chat` takes `{ message: UIMessage, threadId?: uuid }` — ONE message, not an array**: the question is that message, and the history is loaded from the store by `threadId` (`convertToModelMessages` still returns a **Promise** — the `await` is not optional). Without a `threadId` the route opens a new thread and streams its id back as a `data-thread` part, which is how the browser learns the URL to put in the address bar. That control part is filtered out before the answer is saved. **Since the 06. alkalom the answer goes out as an AI SDK MESSAGE stream (`text/event-stream`), not as plain text** (`createUIMessageStream` + `writer.merge(toUIMessageStream({ stream }))` + `pipeUIMessageStreamToResponse`). The reason is not speed: a character stream **cannot carry a tool call**, so the browser could never know what the agent did. The message stream sends typed parts (`text` **and** `tool-runSql` **and** `tool-searchKnowledge`, input and output), which is what the tool cards are drawn from. Five guarantees on this route — four came out of the #4 PR review, the fifth from the 07. alkalom — and each is pinned by a spec; do not undo them:
  - **The role is pinned, not inherited**: the route passes `role: 'customer'` explicitly. Without it the module-level `CURRENT_ROLE` decides — and `user-role.ts` invites you to flip that constant to `admin` for a demo, which behind an open `cors()` would make the unauthenticated endpoint admin-capable.
  - **The request shape is validated, not cast**: `UiMessageSchema` (a `looseObject` with a `role` enum and a `parts` array) fails a malformed body with a Hungarian 400. It used to be `z.array(z.unknown())` plus an `as UIMessage[]` cast, so a `parts`-less message threw a `TypeError` deeper in and Express answered **500 with an HTML stack trace**. One narrow `as unknown as UIMessage[]` remains at the SDK boundary — on already-validated data, because `UIMessage.parts` is a discriminated union no loose schema can structurally match.
  - **The lazy content type is the one guarantee the new protocol OVERRODE** — the intent survives, the mechanism does not. The message stream's headers are written by the SDK (`text/event-stream`), and a mid-run failure now leaves as an `error` **part** with the Hungarian message (`onError`), status 200, instead of a 500 JSON body. What the guarantee was protecting — no stack trace leaks, the client gets a meaningful error — still holds, and a spec pins it. The 400 JSON branch of request validation is **unchanged**: it runs before any streaming.
  - **The history comes from the STORE, not from the request** *(07. alkalom)*: the browser sends only the new message, and the route loads the earlier turns over `threadId`. While the client sent the whole array, anyone could POST a fabricated "you promised 90% off" history and the model would answer from it. A spec pins that a `messages` array in the body is ignored.
  - **A run with no text still answers**: if not a single delta went out (e.g. the step budget ran out), `result.answer` — the agent's `emptyAnswer` — is written before `res.end()`. Otherwise the browser got an empty bubble with a 200 while the CLI showed a real message.

  If a chunk has already gone out, an error can only close the stream — the headers are no longer changeable.
- `apps/web/src/App.tsx` — the browser chat: `useChat` (`@ai-sdk/react`) + **`DefaultChatTransport`** (it was `TextStreamChatTransport` until the 06. alkalom), so the answer builds up word by word **and** the tool steps appear as cards above it — first what the agent did, then what it says. Markdown rendering, an "Állj" (stop) button, and smart auto-scroll: the intent is recorded **on scroll** (`lib/scroll.ts`, `isNearBottom`), so a reader who scrolls up mid-stream is not yanked back down. Since the 07. alkalom it also has memory: a `ThreadList` sidebar fed by `GET /api/threads`, a `?thread=<uuid>` URL that restores the conversation **with its tool cards**, and `prepareSendMessagesRequest` that uploads only the new message. The `threadId` is a **ref, not state**: the transport is created once and its closure must see the current value.

## What this project is

`szoba-kertesz`: a CLI AI agent for an interior-designer persona. It translates Hungarian natural-language questions into read-only SQL over a plant catalog (`products` table) and returns natural-language answers, so assembling a plant package for a room doesn't require SQL knowledge. Full business requirements: `docs/brs-szoba-kertesz.md`.

## Local database

- `docker-compose.yml` runs Postgres 16-alpine via OrbStack, host port `5433` → container `5432`. Start with `docker compose up -d`.
- `init.sql` (mounted into `docker-entrypoint-initdb.d`) creates the `_ro`/`_rw` agent roles **and their grants** on a fresh container — see below for the other two roles (`_chat`, `_package`), whose grants live only in their migrations. The authoritative source of the `_ro`/`_rw` grants is the `<ts>_db_roles` **migration** — keep the two files' content in sync, and change the migration first.
- `.env` defines five connection strings — always keep this split when writing code that touches the DB:
  - `DATABASE_URL` — admin/read-write, for Prisma (schema, migrations, seed).
  - `DATABASE_URL_READONLY` — the `szoba-kertesz_ro` role; this is the **only** connection the agent's read-only tools (`runSql`, `listCategories`) may ever use.
  - `DATABASE_URL_READWRITE` — the `szoba-kertesz_rw` role; the ingest agent's `upsertProduct` path only. SELECT + INSERT + UPDATE on `products`, **no DELETE, no DDL**. Optional in `config.ts`: without it the query side works fully and only `ingest` fails.
  - `DATABASE_URL_CHAT` — the `szoba-kertesz_chat` role; the conversation store **only**: SELECT + INSERT on both `threads` and `messages`, plus UPDATE on `threads` alone (that is what steps `updated_at`). Nothing else — no `products`, no `customers`, no `knowledge_chunks`, no DELETE anywhere, and **no UPDATE on `messages`**, so a stored turn cannot be rewritten afterwards. The `messages` UPDATE was revoked in the `<ts>_messages_append_only` migration after the #8 PR review: the store never updates a message, so the grant was wider than the code, and "append-only" was a claim the database did not back. Two specs measure it. The server refuses to boot without it (fail-fast, Hungarian message), and the CLI's interactive mode needs it too; the one-shot `pnpm cli ask` does not.
  - `DATABASE_URL_PACKAGE` — the `szoba-kertesz_package` role; the package-agent's `validatePackage`/`savePackage` path **only**: SELECT on `products` and `customers` (deterministic checks, not model-generated SQL), plus SELECT + INSERT on `packages` and `package_items` — no UPDATE, no DELETE, so a saved package is **append-only**, same shape as `_chat`. Optional, same as `DATABASE_URL_READWRITE` and `DATABASE_URL_CHAT`: without it the catalog/care question-answer side works fully and only package building fails, with an explicit Hungarian message (`db-package.ts`).
- `init.sql` runs the `CREATE ROLE` for all **four** agent roles on a fresh container (the admin user comes from the container's own env), but the authoritative source of every **grant** is always a migration, never `init.sql`: `<ts>_db_roles` for `_ro`/`_rw`, `<ts>_chat_role` (07. alkalom) for `_chat`, `<ts>_package_role` for `_package`. `init.sql` runs before any table exists, so for `_chat` and `_package` it can only create the empty role — the grants have to wait for their own, later-timestamped migration, which must run **after** the tables it grants on (`threads`/`messages`, `packages`/`package_items`) already exist, or the `GRANT` would target tables that are not there yet.
- `OPENAI_API_KEY` — **optional** (`config.ts`), and the only non-Anthropic key in the project. The embedding model (`text-embedding-3-small`) needs it: both building the knowledge base (`pnpm knowledge:ingest`) and every `searchKnowledge` call embeds text with it. Without it the catalog side works fully — `runSql`, `listCategories`, the CLI, the web chat — and only the knowledge-base path fails, with an explicit Hungarian message. HyDE and the reranker are **not** affected: those run on Claude Haiku.
- **Buktató:** a `process.loadEnvFile()` **nem írja felül** a shellben már beállított változót. Ha egy `.env`-beli kulcsra hitelesítési hiba jön, először nézd meg, nem árnyékolja-e egy shell-változó (`~/.zprofile`); ilyenkor `env -u OPENAI_API_KEY <parancs>` a megkerülés.
- `.env`, `.env.bak`, and `.mcp.json` are gitignored — never commit them. A Prisma MCP server is configured in `.mcp.json` (`npx prisma mcp`) for schema/migration work.

## Architecture (Nx monorepo — scaffolded)

`docs/architektura-monorepo.md` specifies the structure, now in place:

```
packages/core   agent logic — agents/ (agent-loop + one dir per agent),
                tools/ (one dir per tool), rag/ (knowledge base),
                threads/ (conversation store), user-role, trace, logger, config
packages/db     Prisma lib (schema, migration, client, seed) — NOT at repo root
apps/cli        CLI (`ask` + `ingest` commands + persistent interactive mode)
apps/server     Express layer over the core (`POST /api/chat` + `/api/threads`)
apps/web        Vite + React chat (useChat, streaming, thread list)
apps/mcp        MCP-szerver (09.) — stdio, 3 tool: search_plants / search_knowledge /
                ask_szobakertesz; a hívó egy IDEGEN host modellje
tools/autotest  MÉRŐESZKÖZ (08.) — Playwright battery + RAGAS RAG-eval + riportok
```

Key design invariants to preserve:

- **Framework-agnostic core**: `packages/core` must not know about its entry point (CLI/API/web). A new surface is a new app, not a rewrite. Unchanged by the SDK migration — and since the 05. alkalom **three** entry points (CLI, HTTP, browser) drive the very same loop, which is the proof of this invariant, not an exception to it: `core` gained no server-specific code.
- **An agent = prompt + tools + loop**: the loop is shared (`agents/agent-loop.ts`); what distinguishes agents is only their `AgentDefinition` (system prompt, toolset, step limit, token budget). A new agent is a new directory under `agents/`, not a new loop.
- **The role switches a capability, not a prohibition** *(05. alkalom)*: as `admin` the `delegateToIngest` key goes **into** the query agent's toolset object; as `customer` the spread lands empty — the model does not even know the tool exists. This is stronger than a prohibition stated in the prompt: what is not offered cannot be called. The `role` deliberately lives on `AskAgentOptions`, **not** on `AskOptions`: the shared loop does not know which agent it runs, so it cannot know about roles either — it only sees the finished toolset. Two pinning specs (`query-agent.spec.ts`, `ingest-agent.spec.ts`) hold both toolsets in place. The HTTP surface does **not** inherit this switch: `apps/server` pins `role: 'customer'` on every request, so flipping `CURRENT_ROLE` for a CLI demo cannot leak admin capability onto an unauthenticated endpoint.
- **An agent can be another agent's tool** *(05. alkalom)*: `delegateToIngest` looks like any other tool to the outer loop (same `ToolOutcome` back to the Trace), but inside it a **full second loop** runs, with its own prompt, its own toolset and its own DB privilege (`szoba-kertesz_rw`). It never throws — an inner failure becomes Hungarian text for the model, so a failed ingest cannot take the outer loop down with it. The embedded run writes **its own** JSONL line and its own Trace, so one admin delegation produces **two** log entries. That is deliberate: those tokens really were spent, and swallowing the run would make the cost estimate undercount.
- **Five DB connections, five privilege levels**: `DATABASE_URL` (Prisma, admin) · `DATABASE_URL_READONLY` (`szoba-kertesz_ro`, the query agent's `runSql`/`listCategories`/`queryCustomers`, SELECT-only) · `DATABASE_URL_READWRITE` (`szoba-kertesz_rw`, the ingest agent's `upsertProduct`, no DELETE/DDL) · `DATABASE_URL_CHAT` (`szoba-kertesz_chat`, the conversation store only) · **`DATABASE_URL_PACKAGE`** (`szoba-kertesz_package`, the package-agent's `validatePackage`/`savePackage` path). The fourth role is the one that shows the principle is not decoration: `threads` and `messages` are explicitly **revoked** from `_ro`, so the agent that writes the SQL cannot read the conversations — measured: `permission denied for table messages`. And in the other direction the chat role sees neither `products` nor `customers` nor `knowledge_chunks`, and cannot DELETE its own rows either. A prompt-injected "SELECT * FROM messages" therefore fails at the Postgres level, not at the prompt level. No agent ever queries through Prisma, and the query agent **does not even see** the writing tools — the split is enforced in the tool layer *and* at the Postgres role level. This holds for the admin role too: an admin query agent gets `delegateToIngest`, not `upsertProduct`, so the write still happens inside the other agent, on the other role. **The knowledge base follows the same split** (`rag/knowledge-store.ts`, two pools in one file): searching (`searchChunks` / `listSources` / `listChunks`) runs on `DATABASE_URL_READONLY`, loading (`clearKnowledge` / `insertChunks`) on `DATABASE_URL`. That matters because the *search* is what the public, `cors()`-open server calls on every care question — on the admin pool it would open an admin-privileged connection per request, out of the very module that also exports `clearKnowledge()` (TRUNCATE). The admin connection is now needed **only** by the loader script. The `szoba-kertesz_ro` role sees each table through an **explicit** `GRANT`, not a default privilege — since the `<ts>_ro_explicit_grants` migration (#8 PR review), which revoked the earlier `ALTER DEFAULT PRIVILEGES` precisely so a future non-catalog table (like the package tables) would not become readable automatically — measured: SELECT works, DELETE is `permission denied for table knowledge_chunks`. Two specs pin which variable each path binds to. `knowledge-store.ts` still parses those two variables with its **own** `EnvSchema` rather than `config.ts` (`loadConfig()` does not know `DATABASE_URL`, and that stays so). **The fifth role (`szoba-kertesz_package`) is append-only, like `_chat`**: SELECT + INSERT on `packages` and `package_items`, no UPDATE, no DELETE, so a saved package cannot be edited or removed afterwards. It also gets a narrow, cross-cutting SELECT on `products` and `customers` — not for model-generated SQL, but for `checkPackage`'s own fixed queries (`tools/package/package-validation.ts`) that re-verify price and stock right before the write. `db-package.ts` is the first pool in the project to need a **transaction helper** (`withPackageTransaction`): `savePackage` writes to two tables, `packages` and `package_items`, and the single-statement `ON CONFLICT` trick behind `upsertProduct` does not apply across two different tables.
- **One write path only, and the key is enforced by the DB**: the catalog can be changed exclusively through `upsertProduct` (strict Zod at the boundary, parameterized SQL, column names from a code-fixed list, upsert keyed on latin name). Raw write SQL does not exist in the codebase. The upsert is a **single atomic statement** — `INSERT … ON CONFLICT (lower(latin_name)) DO UPDATE … RETURNING id, (xmax = 0) AS created` — backed by the `products_latin_name_lower_key` unique index (`<ts>_products_latin_name_unique` migration). It used to be SELECT-then-INSERT/UPDATE, and two concurrent upserts on the same name produced **two rows**: both SELECTs came back empty before either INSERT ran. Same principle as the role split: the invariant lives in Postgres, not in the prompt and not in the code. Change the index expression and the `ON CONFLICT` target together — they must match.
- **Loop on the AI SDK, mechanics still visible** *(changed in the 04. alkalom — a deliberate decision, not drift)*: `askAgent`/`askIngestAgent` run on the Vercel AI SDK 7 with `stopWhen: isStepCount(n)` instead of the hand-rolled loop of the 2–3. alkalom — since the 05. alkalom on `streamText`, on **one** path: if there is no `onTextDelta`, the stream is consumed anyway. The hand-rolled version is what makes the framework legible: the `for` loop → `stopWhen`, the `executeTool` switch → the tools' own `execute`, the manual message-appending → the SDK. Transparency is preserved on the `prepareStep`/`onStepEnd` hooks (same Trace, same JSONL). Test mocks therefore serve `doStream`, not `doGenerate`, and the chunks are provider-level (`finishReason: { unified }`, nested `usage`, and the text field is `delta` — in the ai-level `onChunk` the same thing is `text`).
- **Transparency by default — two complementary traces, neither replaces the other**: (1) JSONL (`logs/<timestamp>.jsonl`) via `logger.ts`: system prompt, messages, generated SQL, result, response, token usage — this is the evidence base for cost estimates. **A run that dies mid-flight is logged too** (`answer: "[MEGSZAKADT] …"`, with the tokens spent up to that point, summed per step in `onStepEnd` because `result.usage` only exists on success) and the original error is then rethrown unchanged — otherwise a rate-limited or failed run would burn tokens and leave no trace, and the cost estimate would silently undercount. **Under `streamText` this guarantee hangs on `onError` — do not remove it** (measured on `ai@7.0.66`): `streamText` does not rethrow, neither synchronously nor while the stream is consumed. On a first-round failure `await result.text` rejects with the SDK's own wrapper (`"No output generated. Check the stream for errors."`) and the original cause is lost; on a **second**-round failure it does not reject at all, so the run would *look* successful with an empty answer and an interrupted run would get a normal log line. That is why the loop catches the error in `onError` and decides for itself after the stream finishes. Three specs in `agent-loop.spec.ts` gate exactly this. The two traces are independent: neither a failing `log()` nor a failing `trace.finish()` may take the other down; (2) the live `Trace` (`trace.ts`): colored console output plus a turn-structured `logs/<timestamp>.json`, and a continuous `logs/agent.log` watch log for `tail -f`. `--show-prompt` dumps the full message array; `--quiet` silences only the console half. In tests, `print: false` and `persistTrace: false` keep both quiet so no artifacts are written.
- **Prisma lives in `packages/db`**, not the repo root, so the schema is part of the Nx dependency graph and the seed script imports the generated client from there. **`packages/core` does not import Prisma at all** — measured: the only match for `@prisma/client` in `packages/core/src` is a comment saying so. Every runtime DB access in the core goes through `pg` pools, one per privilege level.
- **A mérőeszköz nem a termék része** *(08. alkalom)*: a `tools/autotest` külön workspace-csomag, és a `packages/core` **egyetlen sorral sem tud róla** — a 08. körben a `core` diffje üres. A battery a valódi HTTP/UI felületen mér, a RAG-eval a már exportált `retrieveKnowledge`-en; egyik sem kért hookot a loopba. A termék-oldalon összesen **négy `data-testid`** került az `apps/web`-be, mert a buborékoknak nem volt stabil horguk — és azokat egy spec pinneli, mert egy törött selector nem pirosat, hanem **NÉMA ZÖLDET** adna.
- Before coding against a new or rarely-used library API (e.g. Prisma), look up current docs via Context7 first — reduces errors under test.

## Domain model: `products`

Full schema in `docs/tech-stack.md`. Column semantics (Hungarian) — the agent's whole job is answering correctly against these:

- `category`: szobanövény / kerti / pozsgás / kaktusz / fűszer / fa-cserje / lógó / virágzó
- `location`: beltéri / kültéri / mindkettő
- `light`: árnyék / alacsony / közepes / erős / direkt nap
- `watering`: ritka / közepes / gyakori / állandóan nedves
- `difficulty`: kezdő / haladó / profi
- Effective price is always `COALESCE(sale_price, price)` — `sale_price` is null when there's no active discount.
- `current_height_cm`/`max_height_cm`/`current_pot_cm`: current vs. mature size and pot size, used for room-fit reasoning.
- `pet_safe` / `kid_safe` / `air_purifying`: boolean flags.

## Agent behavior contract

`docs/system-prompt.md` is the actual product-agent system prompt (not a Claude Code prompt) — the **query agent's** schema-context must match it exactly. Rules baked into it:

- SELECT only, ever — no INSERT/UPDATE/DELETE/DDL. Enforced at the DB role level (`szoba-kertesz_ro`), not just by prompt instruction. (The ingest agent is the deliberate exception: it has its own prompt and its own role, and even there writing is possible only through `upsertProduct` — DELETE and DDL are denied by Postgres for `szoba-kertesz_rw` too.) The admin role does not loosen this: `ADMIN_PROMPT_BLOCK` spells out that the query agent never writes itself, only delegates, and that its `runSql` stays SELECT-only.
- Always include a LIMIT.
- Text search via ILIKE.
- Ask a clarifying question instead of guessing when budget, room constraints, or quantity are missing from the request.
- Never invent columns or tables.
- Az orchestrátor sosem válaszol saját szóval — a route-olt agent válaszát adja vissza szó szerint; a package-agent sosem fut SQL-t közvetlenül, mindent az `askInfoAgent` toolján keresztül olvas.

## Conventions (`docs/konvenciók.md`)

Project-agnostic TypeScript conventions (full detail in the doc). Highlights that aren't obvious defaults:

- `unknown` for untrusted/external input, never `any`.
- No mutation — spread into a new object instead of mutating in place.
- Zod validation at system boundaries, fail fast.
- No `console.log` in product code — structured logger only.
- Files ~200-400 lines (max 800), organized by feature/domain, not by type.
- **Prompts the product sends to the LLM** (system prompt, `askAgent` messages) are structured with XML-like tags (`<role>`, `<schema>`, `<rules>`, `<examples>`, ...) to reduce hallucination. This does **not** apply to prompts written for Claude Code itself, which stay natural language.
